# Threat model (PoC, Plan 2)

Scope: the `auction_engine` program, the three stablecoin hooks, and their interaction with the token program on LEZ v0.2.4 (public transactions). Off-chain clients (Plan 3) and the GUI (Plan 4) are out of scope here except where they must follow a rule stated below.

The per-instruction checklist, and the code-review proof of ADR-019 invariants (i)–(iii) with every chained-call site, are in [`docs/architecture/security-checklist.md`](docs/architecture/security-checklist.md).

## Trust assumptions

- **Upstream programs are trusted**: the vendored stablecoin (lez-programs `64c01210` + our hooks) and the token program. PDA authorisation is inherited down the call chain (lee `validated_state_diff/mod.rs:262-290`): an account the engine authorises for the host stays authorised for every program the host calls. The host only chains to the token program of its own position vault.
- **No reentrancy guard exists in LEZ v0.2.4.** R1 (no re-entrant liquidation) rests on our programs: the engine never calls back into itself, and the host never calls the engine.
- **The sequencer is sequential.** There are no write conflicts; a transaction whose precomputed addresses are stale fails.
- **Time** comes only from `CLOCK_01`, which reads the previous block's timestamp.
- **The host trusts the engine for the custody destination and the minimum seizure.** `liquidate_position` checks that custody is an initialised holding of the collateral definition owned by the vault's token program, not that it is the engine's own vault; and it bounds only the *maximum* seizure for a given cover (proportional bound), not the minimum, so an engine could clear debt while seizing little. The real engine always passes the position's full collateral and normalised debt read in the same transaction and always names its own fresh `["VAULT", auction]` PDA as custody (`docs/architecture/security-checklist.md`, invariant (iii); invariant 10 test `inv10_debt_clear_matches_seizure_over_full_chain`). This is part of what binding an engine config delegates (ADR-026/027).

## Authentication of the engine (ADR-019, ADR-026, ADR-027)

- Hooks require Variant C: `caller_program_id == LiquidationEngineState.engine_program_id` **and** the bound engine-authority PDA authorised. Tests: `stablecoin_program::liquidation_hooks::tests`, `security.rs`.
- The engine authority is `["ENGINE_AUTH", config]`: only the config the host admin bound can act on that host. A rogue config created against the same host — even with the same salt, since the config PDA includes its admin (`["CONFIG", admin, salt]`) — is rejected by the hook (`rogue_config_with_the_same_salt_cannot_liquidate_the_bound_host`, `nobody_can_squat_the_admins_config_address`). **Bind-time verification:** the host admin reads the `EngineConfig` before binding (admin, host ids, token program id, parameters); see `docs/architecture/hooks.md`.
- **Instant rebind; admin-key compromise.** `set_liquidation_engine` takes effect in the transaction that calls it: there is no timelock or delay. Whoever holds the host admin key can bind any engine program and authority at once, and that engine can then seize every unsafe position (within the host's health check and proportional bound) and freeze new debt. A compromised *engine* admin key cannot move auction, buffer or surplus funds (no admin path exists, row 10 below) but can retune the bounded parameters, pause collateral types, lower `bad_debt_freeze_threshold` or disable the protocol token so that anyone's `check_solvency` freezes the host, and step the reference price by up to 2x per change. Mitigation for the PoC: both admins are user keys held by the operator; every change is logged in `DEPLOYMENTS.md`. A timelocked or multisig admin is a production item (and a PDA/multisig host admin cannot call `set_liquidation_engine` at all, below).
- **Config-chosen program ids (I4).** The engine only chains to the program ids stored in its config, fixed at `init_config` from the accounts it was given; a config built on a fake host or token program is accepted on-chain (`fake_host_config_is_accepted_so_clients_must_verify_program_ids`) and would receive the signer flags users attach (holdings that sign). The defence is client-side: the SDK/CLI refuses any config whose `host_program_id` / `token_program_id` differ from `DEPLOYMENTS.md`.
- **Published ImageIDs are reproducible (I4, ADR-047).** The deployable guests are built with the upstream Docker recipe (builder image pinned by digest), committed in `artifacts/guests/` with sha256 and ImageIDs in `artifacts/guests/manifest.json`, and CI job `guest-repro` rebuilds our two guests (stablecoin, auction_engine) from source on every push and pull request touching their inputs and requires identical bytes, and checks every committed binary against the manifest (sha256 and ImageID). The three upstream guests (token, twap_oracle, token_mint_authority) are rebuilt from the pinned lez-programs 64c01210 source only on the scheduled (weekly) and manual (`workflow_dispatch`) runs; on push and pull request they are only hash-checked against the pinned manifest; the ids in `deployments/localnet.json` equal the manifest (`guest_manifest_matches_the_localnet_deployment`), and `DEPLOYMENTS.md` is kept equal to them by hand (no test reads it). A client that verifies program ids against `DEPLOYMENTS.md` can therefore check them against a rebuild, but still trusts whoever publishes that file for which build is the intended one. The client also trusts its RPC endpoint: there are no state proofs, so a malicious sequencer URL can serve consistent fake accounts that pass every client check.
- Invariant (i): the engine supplies `ENGINE_AUTH` seeds only on calls to `EngineConfig.host_program_id`; the engine chains only to the program ids stored in its config, and no instruction argument is a program id (documentation test `engine_takes_no_program_id_argument`). Invariant (ii): the host chains only to the vault's token program. Invariant (iii): hook amounts come from the position read in the same transaction; every forwarded account id is re-derived or checked against `EngineConfig` (`foreign_account_as_position_is_rejected`). The tests prove the *host* guard (laundering through the test-only `flawed_engine`, ADR-034); invariant (i) for the *real* engine is proved by code review: every chained-call construction site, its target program id and its seeds are enumerated in `docs/architecture/security-checklist.md` (Task 19).
- **Upstream laundering note.** The host's existing admin and freeze checks are plain `is_authorized` assertions (`programs/stablecoin/src/checks.rs:123`, `src/freeze.rs:58`). If the admin or freeze authority were a PDA, a program it authorised could launder that authority onward. The new `set_liquidation_engine` requires a top-level call; for the existing instructions, admin and freeze authorities must remain user keys (stated in the upstream PR).
- Zero ids: SPEL reports a zero `caller_program_id` for top-level calls, so zero engine program ids and authorities are rejected at bind time and zero ids at engine config time.
- Private path: the immediate-caller check also holds in the privacy circuit (`private_path_impostor_is_rejected_by_the_immediate_caller_check`); `liquidate` is not private-capable on v0.2.4 (ADR-034).

## Specific residuals (ADR-024 obligations and spec §10)

- **S5 residual (pause onset).** Policy (b) derives the stale onset from `last_seen_oracle_ts + max_age`. A producer that re-stamps an unchanged price keeps the feed "fresh"; publishes nobody observes are reconstructed at the next observation, and a reverted observation is lost (ADR-032). An adversary gains at most one block of extra discount (S5 property test). Keepers and the app call `observe_feed` on refresh.
- **Final-fill bound.** A target-reaching fill whose plain floor is 0 pays exactly 1 collateral base unit, at most once per auction (ADR-024), so a sub-unit remainder cannot strand an auction.
- **Oversized-alone limitation, both directions.** While an oversized auction is live its reservation exceeds the cap, so every other liquidation of the instance waits; conversely any live small auction makes a whale wait. Partial liquidation (M1) is the real fix (`oversized_auction_blocks_others_and_small_auction_blocks_whale`).
- **Keeper reward in a shortfall.** The reward is carved from the penalty; when the lot does not cover the debt it comes out of collateral that would otherwise reduce bad debt. `reward_cap` and `reward_coll ≤ c` bound it (`underwater_reward_is_capped_at_the_seizure`).
- **Unsold auction keeps its cap reservation** (no expiry, ADR-012); visible on-chain and to be shown by the CLI/GUI.
- **Donation griefing.** Anyone can raise any holding; balances are compared with `>=` only and sweeps take the whole balance (ADR-033). Donations into a lot-0 auction vault are stranded (donor's loss). More generally, a donation into **any auction vault that has no outstanding claim at donation time** is stranded: a vault whose auction settled with no leftover, whose leftover was already claimed, or that was settled by `settle_empty`; no later instruction sweeps it. So is a donation into the vault of a **fully taken surplus auction**: it ended at its last take and cannot be closed, so `close_surplus_auction` never returns that vault to the buffer. No booked number and no protocol value is affected; the donor loses the amount.
- **List-capacity griefing** is avoided by having no on-chain auction list (ADR-008).
- **Mock-token mint authority.** Only `["MINT_AUTH", config]` can mint, and only `take_debt` asks it to, for `floor(offered × filled / debt_lot) ≤ max_mint_per_auction`.
- **The mint cap rests on the parameter lock and on `debt_live`.** "Total minted over one debt auction ≤ `max_mint_per_auction`" holds because every take prorates an offer capped by the *current* `max_mint_per_auction` against the *current* `debt_lot`, and the fills sum to at most the lot. That needs (a) the system parameters to stay fixed while the auction is live (`set_engine_params` refuses with `ProtocolTokenLocked` while `debt_live`), and (b) `debt_live` to change only with the auction: set by `start_debt_auction`, cleared only by the last take or `close_debt_auction`. Any future instruction that clears `debt_live` or edits system parameters must preserve both (`multi_take_over_time_never_mints_more_than_the_cap`).
- **No freeze with a working protocol token.** If debt auctions keep closing untaken, `check_solvency` never freezes; governance must monitor (ADR-017).
- **Host freeze scope.** The host freeze also blocks `open_position` and `withdraw_collateral` (`no_protocol_token_freezes_above_threshold_and_only_the_freeze_authority_unfreezes`); only the freeze authority's `unfreeze` lifts it.
- **Immediate re-freeze.** `check_solvency` is permissionless and the engine never unfreezes. If the freeze authority unfreezes while settled `unbacked_debt` is still above `bad_debt_freeze_threshold` (and no working protocol token exists), anyone can freeze the host again in the next transaction (`second_check_on_a_frozen_host_is_a_harmless_refreeze` shows the freeze is idempotent). Unfreeze only after restoring solvency (runbook below), or with the protocol token reconfigured.
- **Governance trust in the engine admin (I5).** A single reference-price change is bounded to [old/2, 2·old], but repeated changes are not; the admin can switch the protocol token, or disable it, whenever no system auction is live. Disabling it with `unbacked_debt > bad_debt_freeze_threshold` lets anyone's `check_solvency` freeze the host. Every change is logged in `DEPLOYMENTS.md` (ADR-017).
- **Protocol token set to a non-token account: fixed (ADR-038).** `init_config` and `set_engine_params` require an enabled protocol-token slot to be a fungible token definition owned by the config's token program (`ProtocolTokenMismatch`; tests `init_config_requires_the_protocol_token_to_be_a_fungible_token_definition`, `protocol_token_must_be_a_token_definition_at_config_time`, `admin_cannot_point_the_protocol_token_slot_at_a_fund_account`). The mint authority is still checked at use time, because the token program can rotate it; a token without `["MINT_AUTH", config]` as authority keeps `MintAuthorityMissing` as a `check_solvency` freeze reason (spec §5.11). The use-time `ProtocolTokenMismatch` checks stay as defence in depth; on-chain they are no longer reachable for a validated slot.
- **Manipulated-but-valid reference oracle (M14).** A reference oracle that passes validation can move the effective price by up to ±20% of the admin price; near the `max_mint_per_auction` boundary that can flip `start_debt` into `MintCapConfig` and so make `check_solvency` freeze the host. In the other direction the same ±20% can turn a legitimate `MintCapConfig` (a start amount above the cap at the admin price) into a startable auction, hiding a freeze that should happen. Mitigation: keep the admin price's start amount well inside the cap.
- **Debt-auction relist griefing: mitigated (ADR-039).** `start_debt_auction` refuses (`DelayNotElapsed`) within `DEBT_RELIST_DELAY_MS` (10 min) of the previous debt auction's end (`close_debt_auction` or the final take), so after any end the admin has a window with `debt_live == false` in which `set_engine_params` can change the protocol token, its oracle or the system parameters (`a_closed_debt_auction_cannot_be_relisted_before_the_delay_so_the_admin_can_swap_the_token`, `the_griefing_loop_leaves_the_admin_a_window_after_every_close`). Residual: a griefer can still keep one auction live for `system_ttl_ms` and relist after the delay, so the lock is held for most of the time and the admin has a guaranteed 10-minute window only after each end, not continuous control; while an auction is live `check_solvency` reverts `RecoveryInProgress` (spec §5.11 behaviour). During the relist delay `check_solvency` returns `NoAction` with a working token (its dry-run start check does not apply the delay) and still freezes for a broken token. The surplus side relies on the admin-set `surplus_delay_ms` for the same window; set it above zero in production.
- **Top-level-only engine binding (M14).** `set_liquidation_engine` requires `caller_program_id == 0`, so a host whose admin is a PDA or multisig program cannot bind an engine; raised in the upstream PR.
- **Late-landing dropped transaction plus resend (RT-01, Low).** `confirm` reports `Dropped` after five blocks and the CLI advises a re-quote and resend. If the original transaction lands after that, the resend reads the new nonce and also applies, so ADR-042's "at most one applies" holds only when the resend is signed before the late original lands. Each fill is individually correct and no protocol funds are at risk; the user can overspend against their own intent. Parked to M1 (reword the exit-3 message, add a tombstone check and a `confirm.rs` test). Whether the v0.2.4 sequencer can apply a transaction more than five blocks after accepting it was not confirmed.
- **Unpinned risc0 installer in CI (RT-02, Low).** The `install-risc0` action runs `curl | bash` of the installer on every cold cache, including the `guest-repro` job (the I4 reproducibility check, ADR-047) and the optional self-hosted prover. A compromised installer would run code on a CI runner and could undermine the reproducibility claim. Component versions are pinned; the installer is not. M1: pin the installer by hash.
- **Self-hosted prover runs any dispatched ref (RT-05, Low).** With `REAL_PROOF_SELF_HOSTED` set, `real-proofs.yml` runs for any dispatched branch or pushed tag, and `~/.risc0` persists between runs, so a writer's unreviewed commit could replace `r0vm` and later runs on `main` would trust it. The job is off by default and outsiders cannot trigger it (no `pull_request` trigger). Before enabling it, follow the hardening note in `docs/architecture/real-proofs.md`.
- **`[local]` stablecoin commits bypass the patch series (RT-06, Low).** `export-hook-patches.sh` skips commits whose subject contains `[local]` and `check-hook-patches.sh` replays them before comparing, so such a commit can change deployed stablecoin source without reaching `patches/stablecoin` while the check stays green. Today the only one is `0aecfc9` (ADR-035, an `instance-b` feature-gated entry-point change). M1: compare the deployed tree against the patch series, or allowlist the paths a `[local]` commit may touch.
- **Price-band edges (RT-07, Info).** ADR-005's clamp `P = clamp(M, R·lo, R·hi)` has two edges. When the market price `M` is below `R·lo`, the engine pays more collateral per coin than the market rate (the surplus comes out of the owner's leftover or becomes a booked shortfall). When `M > R·hi/(1−d_max)` (a valid feed, for example above 1.57 R at hi = 11000 and d_max = 30%), a bid buys less collateral than its coin is worth at any discount, so auctions hold their reservations (no expiry, ADR-012) until the market returns. Neither is a code defect; keep `lo` close to 10000 in deployments.

## LEZ 0.4 port (Plan 5 slice, `v04/`): accepted differences

The 0.4 engine (ADR-056 to ADR-061) replaces the v0.2.4 authentication above with whole-actor `from` checks; the v0.2.4 sections still describe the deployed PoC. Accepted for the slice (ruling R-9c):
- **Token errors instead of engine errors.** An unsigned or underfunded bid fails with the token's error, not v0.2.4's engine error. `VaultBelowBook` surfaces as the token's `Sweep` floor (`BelowAtLeast`); it is unreachable, because only the engine can debit an auction vault.
- **Bid rooted at the collateral actor, no bidder proxy.** The bidder's signature on its own holding authorises the payment; a proxy would cost two executions and add no check.
- **No program bidders or owners.** The proxy pattern needs a signer, so a program cannot bid or claim a leftover in the slice.
- **A signature authorises the signer's holdings for the whole transaction**, including the host's and oracle's `ReadState` handling. This trusts the programs a config binds (host, oracle, token), as design note §4.3 (c) point 1 already requires.
- **Custody floor, not equality** (ruling R-5e): a donation to a host vault before a seizure stays in the auction vault, unbooked; the engine books the host's report.

## Engine freeze recovery (ops runbook)

1. `check_solvency` froze the host: `ProtocolParameters.is_frozen == true` is the current freeze state. `Accounting.host_frozen_by_engine == true` only says the engine has frozen this host **at least once**: the engine sets it on every Freeze and never clears it, so it stays `true` after an unfreeze and is not a current-state flag.
2. Restore solvency: penalties accumulate in the buffer; anyone calls `settle_debt(u128::MAX)`; or configure a working protocol token and run debt auctions.
3. When `unbacked_debt ≤ bad_debt_freeze_threshold` (or by governance decision), the host's freeze authority calls `unfreeze`. The engine never unfreezes. Unfreezing earlier invites an immediate re-freeze (above).
