# Per-instruction security checklist

Spec §10 checklist, filled from the handler code (`programs/auction_engine/src/*.rs`, each handler's first lines are its checks) and the hooks (`programs/stablecoin/src/liquidation_hooks.rs`). Each cell is "yes — <where>" or "n/a — <why>". Reviewed in Plan 2 Task 19 at HEAD `eb0a1a4`; the result is recorded in [`THREAT_MODEL.md`](../../THREAT_MODEL.md) (Review log). Rows follow Shared Reference R2 order.

How the column "checks → effects → chained calls" holds structurally: a handler is a pure function that returns `Err` before building any output, or returns all post-states and all chained calls at once. lee applies the engine's post-states and then runs the chained calls; any failure reverts the whole transaction. The engine never receives a callback (no program it calls ever calls it), so the remaining obligation is that every chained call's pre-states equal the state after the earlier calls (`token_calls::with_balance` / `post_init`) and that a PDA is flagged authorised only in the call that attaches its seed (R3).

Common helpers: `read_clock` (`CLOCK_01` id and decode), `load_config` / `load_coll` / `load_accounting` / `load_auction` (owner = engine, 8-byte tag, PDA re-derived from stored fields, `config` back-reference), `fungible_balance` (token program = `cfg.token_program_id`, fungible, definition), `check_recipient` (initialised with the definition, or fresh and signed), `optional_slot` / `expect_slot` (ADR-030), `feed::observe` (oracle id = `coll.oracle_id`, `validate_feed`), `feed::redemption_price` (host PDA and owner).

## ADR-019 invariant (i): code-review proof for the real engine

Claim: the engine attaches `["ENGINE_AUTH", config]` seeds only on chained calls whose program id is `EngineConfig.host_program_id`, and every chained call it builds targets a program id read from validated config, never from instruction data or an unpinned account.

Every `ChainedCall` the engine produces is built at one of the sites below (`grep -n "ChainedCall::new\|token_calls::\|buffer_burn(" programs/auction_engine/src/*.rs`, test modules excluded). The guest (`programs/auction_engine/methods/guest/src/bin/auction_engine.rs`) builds none: it passes `ctx.self_program_id` and the accounts to the handler and returns the handler's calls unchanged (`finish`). `auction_engine_core` builds none. The four `token_calls` builders (`token_calls.rs:65,83,102,119`) take the target as their first parameter and attach only the seeds passed in.

Why this proves (i):

1. `ENGINE_AUTH` is attached at exactly two sites (`liquidate.rs:303`, `solvency.rs:130`), both on a call whose target is the literal `cfg.host_program_id`. `MINT_AUTH` is attached at one site (`debt.rs:250`), on a call to `cfg.token_program_id`. The other seeds (`BUFFER`, `VAULT`, `SURPVAULT`) are the engine's own token holdings and go only to `cfg.token_program_id`.
2. `cfg` is always `load_config(&program_id, &a.config)` (`accounts.rs`): the account must be owned by the engine (`program_id` = `ctx.self_program_id`, not caller data), carry `TAG_CONFIG`, and sit at `["CONFIG", cfg.admin, cfg.salt]`. Only the engine writes it: `init_config` sets `host_program_id` / `token_program_id` from the owners of the host's `ProtocolParameters` (PDA-checked) and of the stablecoin definition it names, and `set_engine_params` copies both unchanged (`..cfg`). `liquidate` (`liquidate.rs:323`), a chain-end `bid_with_settlement` (`bid.rs:176`) and `settle_empty` (`settle.rs:50`) write back the config they loaded, changing only `global_reserved`; no handler assigns `host_program_id` or `token_program_id` after `init_config`.
3. `config_id` in the seeds is `a.config.account_id`, the same account `load_config` just validated, so the authority signed for is the one the host bound.
4. No instruction argument is a program id (`engine_takes_no_program_id_argument` over the IDL), and no handler takes a program id from an account other than the config, except `init_config`, which derives it from the PDA-checked host account and records it (I4: a config built on a fake host is accepted, so clients verify the stored ids against `DEPLOYMENTS.md`).
5. Siblings do not share PDA authorisation on the public path (R3), so the `ENGINE_AUTH` authorisation exists only inside the host call and whatever the host chains to (invariant (ii)).

## ADR-019 invariant (ii): the host chains only to the vault's token program

The hooks build one chained call in total: `liquidation_hooks.rs:421`, `Token::Transfer(vault, custody)` with target `token_program_id = vault.account.program_owner` (`:339`) and the vault's own seed. The vault is the position's PDA vault (`verify_position_vault_and_get_seed`, `:321`) of the collateral definition. In the same transaction the engine has already required that vault's owner to be `cfg.token_program_id` (`fungible_balance(&a.host_vault, &cfg.token_program_id, …)`, `liquidate.rs:178-182`), and upstream `open_position` creates the vault with the program that owns the collateral definition. `engine_freeze_new_debt` and `set_liquidation_engine` chain nothing. The `engine_authority` account is not forwarded to the token program, and the token program makes no chained calls, so the inherited authorisation goes nowhere.

## ADR-019 invariant (iii): hook arguments and forwarded accounts come from validated state

- `liquidate` → `liquidate_position(collateral_to_seize, normalized_debt_to_cover)`: both amounts are `pos.collateral_amount` / `pos.normalized_debt_amount` of the position decoded in this transaction (`liquidate.rs:298-301`), after `load_position` checked it is host-owned at `compute_position_pda(cfg.host_program_id, owner, nonce)` from its own stored fields. Forwarded accounts: `engine_authority` = `engine_authority_pda(config)`; `liquidation_engine_state` = `compute_liquidation_engine_state_pda(cfg.host_program_id)`; `position` (above); `host_vault` = `compute_position_vault_pda(host, position)` and = `pos.vault_account_id`; custody = this auction's `["VAULT", auction]`, required uninitialised and initialised in the same transaction; accumulator = `compute_stability_fee_accumulator_pda(host)`, host-owned; redemption state = `compute_redemption_price_state_pda(host)`, host-owned (`feed::redemption_price`); oracle = `coll.oracle_id` = the host's `market_price_oracle_id`; `protocol_parameters` = `cfg.host_protocol_parameters_id`, host-owned; clock = `CLOCK_01`. Test: `foreign_account_as_position_is_rejected`.
- `check_solvency` → `engine_freeze_new_debt()` (no arguments): forwards `engine_authority` (PDA), `liquidation_engine_state` (PDA under the host) and `protocol_parameters` (= config id). The decision reads only engine-owned state and the two pinned optional slots (`caller_cannot_substitute_the_protocol_token_account`, `caller_cannot_inject_accounts_into_unconfigured_slots`, `forwarded_accounts_must_be_the_engine_validated_ones`).
