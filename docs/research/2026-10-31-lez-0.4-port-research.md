# Porting lez-auction-engine from LEZ v0.2.4 to LEZ testnet 0.4: research

Checked 2026-10-31. Research only: nothing in the repo was changed. Tags: **[C]** = confirmed (I read the
source, API output or a live RPC answer), **[I]** = inferred, **[3P]** = what a third party reports, not
checked by me.

Baseline (SUBMISSION.md "Pins", Cargo.toml): LEZ v0.2.4 `47eba256`, SPEL `1ef0500f`, risc0-zkvm 3.0.5,
Rust 1.94, lez-programs `64c01210`, lez_core 0.4.1 `acf0cd50`. `docs/v03-port-plan.md` (checked 2026-10-17)
predicted that the actor model from LEZ PR #935 would become 0.4. **It has.**

## TL;DR

- **LEZ v0.4.0-rc1** is tagged (`1806e873`, 2026-10-29). Its guest model is a full rewrite: actors,
  `actor_entrypoint!`, `Response` and `SyncMessage`/`AsyncMessage`. Fees are mandatory, and the transaction
  format and genesis are new. The rc1 release notes contain **19 breaking (`!`) PRs**. [C]
- **No SPEL release, branch or fork targets 0.4.** The newest SPEL work is a WIP v0.3 (plan/apply) port on a
  fork, and 0.4 has already replaced plan/apply. [C]
- **There is no public testnet 0.4 yet.** `testnet.lez.logos.co` answers as v0.3.x. An external proposal
  reports that the Logos roadmap puts the 0.4 testnet at end of November. [C] / [3P]
- **lez-programs `main` is on LEZ v0.2.5-rc2** and has no 0.4 work. Our 4-patch hook series **already
  conflicts** with `main`. [C]
- **lez_core 0.6.0 for v0.4.0-rc1** exists only as an open PR (#72). It changes
  `send_generic_public_transaction` again. [C]
- Net: S1 ("deployed and tested on testnet 0.4") is **blocked upstream**: there is no network to deploy to.
  U1 (SPEL) is **blocked** too: no SPEL supports 0.4. The program layer is a rewrite, not a bump.
  `auction_core` and the quote/plan math carry over.

## 1. SPEL and LEZ 0.4

- Releases: v0.7.0 (2026-09-17, `4107dcb1`) pins LEZ `tag = "v0.2.4"`. v0.7.0-rc.3 (2026-10-19) is the same
  commit as `main`, `c6f73ce2`, and pins LEZ `tag = "v0.2.5-rc2"` (spel-cli/Cargo.toml and
  spel-ffi-compile-test/Cargo.toml). PR #290 "Make SPEL work with LEZ 0.2.5-rc2" was merged 2026-10-13. [C]
- None of the ~150 branches in logos-co/spel is named for v0.3, v0.4 or actors. [C]
- **spel #291**, "Support LEZ v0.3 (sharded account data, plan/apply execution)", is open and was updated
  2026-10-30. A maintainer said on 2026-10-06 that the v0.3 work had started. The work lives on the fork
  `0x-r4bbit/spel`, branch `chore/lez-0.3.0-compat`, head `0020cf2e` (2026-10-09, commit message "WIP"),
  which pins LEZ `v0.3.0`. Open fork PR `0x-r4bbit/spel#5` fixes v0.3 client-gen problems: fee declaration,
  a hard-coded `gas_limit` of 10M that makes the sequencer reject the transaction with `PayerCannotFund`,
  and FFI timeouts. On 2026-10-30 a commenter reported deploying a program to testnet.lez.logos.co with this
  branch. [C]
- **Gap:** SPEL's macros generate the v0.2.x entrypoint: `AccountWithMetadata` lists, `#[account]`
  constraints and owner checks. Even the v0.3 port emits plan/apply. 0.4 has neither. A guest is one
  `fn(&ReceiveInput, M) -> Response` per actor (see §2). For 0.4, SPEL needs new entrypoint codegen, new
  account/authorization constraints (actor state, `is_authorized`, `from_own_program`, PDA seeds on
  messages), IDL support for events and messages, and client-gen for `FeeDeclaration` and the actor-scoped
  public context. Nothing of this has been started in public. [C for "not found"; I for the scope]
- Other teams are working around it. Proposal rfp #237 (Tessera) writes: "No SPEL release supports v0.3 or
  0.4 … We maintain the IDL in SPEL's JSON schema … until SPEL supports 0.4", and asks whether that
  satisfies U.4. [C, quoting the issue]

## 2. LEZ v0.2.4 → v0.4.0-rc1: what changed for programs and clients

Compare `v0.2.4...v0.4.0-rc1`: 1010 commits ahead and over 300 files changed (the compare API stops listing
at 300). [C]

**Guest API** (`lee/state_machine/core/src/program/mod.rs`; the package is still named `lee_core`) [C]
- The entrypoint is now `lee_core::actor_entrypoint!(handler)`, with `fn handler(&ReceiveInput, M:
  BorshDeserialize) -> Response`. `ReceiveInput { receiver: Actor, from: Option<Actor>, is_authorized,
  pre_state: ActorState, message }`.
- An `Actor` is an `(account_id, program_account_id)` pair. **One handler call sees and writes one actor
  state.** An `Account` is `{ nonce, data: AccountData { actor_states: BTreeMap<AccountId /*program*/,
  ActorState> } }`. There is no `program_owner` and no balance field: the native balance is the actor state
  at `NATIVE_TOKEN_PROGRAM_ID`.
- Effects that touch several accounts are messages. `Response::set_state(..)` or `keep_state()`, then
  `.send_sync(Actor, &msg)` or `.send_async(..)`, `.event(ProgramEvent{selector,data})`, and block or
  timestamp validity windows. Sync messages run depth-first and atomically and **return nothing**: a reply
  is a second message back to `from`. Example `hello_world_with_move_function.rs`: the source clears its
  state and sends `Append` to the destination actor, which checks `from_own_program()`.
- Tail calls and PDAs: `SyncMessage::with_pda_seeds(vec![PdaSeed])`, `AccountId::for_public_pda(&program_account_id,
  &seed)`. PDAs derive from the **deployed program address**, not the ImageID (`tail_call_with_pda.rs`). Open
  issue #974, "consider PDA authorization scheme", means this may still move.
- `ChainedCall`, `AccountWithMetadata` and `ProgramOutput` give zero code-search hits on `dev`. They are
  gone. `ProgramId = [u32;8]` still exists, but programs are addressed by `AccountId` everywhere.
- Deployment goes through the native `program_loader` (`PROGRAM_LOADER_ACCOUNT_ID = [0xFE;32]`,
  `ProgramHeader` plus up to `MAX_PROGRAM_SEGMENTS = 20` segments, an immutability flag). The wallet command
  is `wallet deploy-program <bin>`.

**Transactions** [C]
- `LeeTransaction` has only the variants `Public | PrivacyPreserving`; there is no separate deploy variant.
- A public message is `TransactionMessage<PublicExecution{ root: RootCall{to: Actor, message}, fee:
  Option<FeeDeclaration> }>` plus `public_context` (the declared actors), `nonces` and `admission_evidence`.
  Its domain prefix is `/LEE/v0.3/Message/Public/`. Borsh is used throughout (`de_strict_order`).
- PR #985 (2026-10-29): privacy-preserving transactions now pay fees in-proof. It changes the journal, the
  block body and hash, and requires a **genesis restart**. At most 4 privacy-preserving transactions fit in
  a block.
- [3P, vpavlin's LEZ-V04-NOTES]: every user transaction needs a `FeeDeclaration` signed by the payer. **A
  revert is charged the whole gas limit.** The wallet reserves gas_limit × base_fee_exec.

**RPC** (`lez/sequencer/service/rpc/src/lib.rs`) [C]
- These names survive: `sendTransaction`, `getBlockRange`, `getLastBlockId`, `getAccount`,
  `getAccountsNonces`, `getBlock`, `getTransaction`, `getProgramIds`.
- New: `getFeeState`, `getAccountView(Actor)`, `getPublications`, `getMessagePath`, `getRecoveryBinding`.
  `getProofsAndRoot` now takes message positions.
- Payload types (Block, Account, transactions) all change. Our SDK also calls `get_current_block_height`
  and `send_generic_public_transaction`, which are lez_core module calls, not sequencer RPC.
- `dryRunPublicTransaction` was removed in #985. Dry runs are wallet-local (`lee::simulate_public_transaction`).

**Events** [3P]: the sequencer stores events only for final blocks. A standalone sequencer (mock Bedrock)
never finalizes, so events cannot be queried there. Event-based discovery cannot be the only path in
standalone CI.

**Proving and RISC0_DEV_MODE** [C]
- The README at rc1 still says public transactions "are executed directly on-chain … without proof
  generation". `just run-sequencer-standalone` = `cargo run --features standalone -p sequencer_service`.
- Without the `prove` feature, the binary executes guests with r0vm 3.0.5, which must be on PATH [3P].
- So `RISC0_DEV_MODE=0` with public transactions only is cheap. Only privacy-preserving transactions prove:
  LEZ's own nightly "Valid proof" job says one private proof takes about 60 minutes on a standard runner.
- ADR-045 (public transactions are executed, not proved) still holds. [C/I]

**Toolchain** [C]: risc0-zkvm 3.0.5 (unchanged), `rust-toolchain.toml` 1.98.1 (ours is 1.94), edition 2024.

**Breaking changes per crate** [I, derived from the above]
| Crate | Impact |
|---|---|
| auction_core | none (no_std, no LEZ dependency) |
| programs/auction_engine | rewrite of the shell: each instruction becomes a message conversation across actors (config, auction, vault, bidder holdings, stablecoin), new authorization model, PDAs from the deployed address, no SPEL macros |
| programs/stablecoin + patches | blocked on the upstream port of the host; hooks redone as messages (§4) |
| programs/token, twap_oracle | vendored v0.2.x programs; need the 0.4 ports from lez-programs (none yet). Balances may move to native or wrapped_token actor states |
| crates/auction_sdk | new tx builder (Actor root, public_context, FeeDeclaration, payer signature), new account decoding (actor_states), new PDA math, fee-aware confirmation, scanner on new Block type; enum-index encoders survive as the seam |
| cli | follows the SDK; add fee and payer flags |
| auction_ffi, modules/auction_engine | new lez_core signature (§5) |
| scripts, CI | bootstrap from v0.4 tag; `wallet deploy-program`; 0.4 genesis keys; Rust 1.98.1; fee-funded accounts |

## 3. Public testnet 0.4

- `lez/wallet/src/cli/network.rs` at rc1 points to `https://testnet.lez.logos.co`. [C]
- A live read-only probe of that URL on 2026-10-31: `getFeeState` and `getAccountView` exist, but
  `getPublications` and `getRecoveryBinding` (0.4-only) return "Method not found". Height 70,925. **It runs
  0.3.x, not 0.4.** [C]
- `testnet-legacy.lez.logos.co` is still up and on v0.2.4 (height 23,420, no `getFeeState`). [C]
- No 0.4 endpoint, faucet or deployment rules are published anywhere I could find: not in the LEZ README,
  the docs (only "LEZ testnet v0.1 tutorials"), the rfp README or the appendix. **Not found.**
- rfp PR #214 was **merged** 2026-10-22. RFP-014 now says S1: "delivered for, deployed and tested on LEZ
  testnet 0.4", and S2: e2e "against a LEZ sequencer (standalone mode) with `RISC0_DEV_MODE=0` … in CI". The
  RFP is still `status: closed`, described as "reopening soon". [C]
- Timeline signals:
  - logos-co/ecosystem #251: 0.4 adds a testnet reset; "teams in delivery stay on 0.2.4 … and upgrade to 0.4
    later". The contractor page asks for "their 0.4 transition timeline". [C]
  - rfp #237 states that testnet 0.4's release "was scheduled for the end of November on the Logos roadmap as
    read on 23 October 2026". [3P]
- How other proposals deploy:
  - #187 (Antumbra, RFP-014 competitor): deployed on the public **v0.3** testnet and re-checked by a script
    against `testnet.lez.logos.co`. It promises "redeployed … on testnet 0.4 within days of its launch".
  - #236 (Ostrakon): written for the 0.4 actor model.
  - #237 (Tessera): a prototype on LEZ `dev` `7e3f7f76`. Real receipts are settled in-process through `lee`,
    plus a **standalone sequencer** run in dev mode with a `program_loader` deploy. It waits for the public
    testnet. [C, quoting the issues]

## 4. lez-programs main vs 64c01210

- `main` = `6674d783` (2026-10-28), 116 commits ahead. It pins LEZ `tag = "v0.2.5-rc2"` and still uses
  risc0 3.0.5. [C]
- Upgrade branches:
  - `chore/upgrade-to-lez-0.3.0-rc` (`4b4e8b8`, 2026-10-12, "WIP: LEZ v0.3.0 upgrade") pins v0.3.0.
  - `chore/lez-core-0.4.3` is v0.2.4.
  - Issue #445 builds on `refactor/lez-v0.2.5`.
  - **No 0.4 branch.** [C]
- Stablecoin diff 64c01210..main: 30 files, +2745/-1154. [C]
  - **Instruction enum:** a new `reset_redemption_rate_controller` is appended after `unfreeze`, so it takes
    variant 21. Our patches append `set_liquidation_engine`, `liquidate_position` and
    `engine_freeze_new_debt` at the same position, so **our indexes shift** after a rebase, and so do our SDK
    encoders.
  - **ProtocolParameters:** new caps `MAXIMUM_STABILITY_FEE_PER_MILLISECOND` (about 100%/yr),
    `MAXIMUM_CONTROLLER_PROPORTIONAL_GAIN` and `..._INTEGRAL_GAIN`. `compute_protocol_parameters_pda` now
    takes the program `AccountId` instead of a `ProgramId` (the deployed-address model already arrives in
    v0.2.5-rc2).
  - Commit `7222e852` ("launch like RAI"): **`generate_debt` no longer takes the oracle account**, the oracle
    may not exist yet, and a missing oracle is read as "no observation". Account lists change.
  - Commit `b4938287`: accrued fees are minted to the surplus holding.
- Oracle scale: **#401 is a PR** ("network-agnostic stablecoin deployment", open), not the scale issue. The
  Q64.64-vs-1e27 fix is now tracked in **#445** "SC-NORM" (open; conversion `floor(priceQ64 * 1e27 / 2^64)`,
  built on `refactor/lez-v0.2.5`) and #424. It is not fixed on `main`. [C]
- Patch series: `git apply --check` passes on 64c01210. On `main`, 3-way apply **conflicts** in
  `core/src/lib.rs`, `guest/src/bin/stablecoin.rs` and `src/liquidation_hooks.rs`. Patches 0002 and 0003
  then fail on the conflicted index. (Tested in a scratch clone.) [C]
- In spirit: the hook design (an engine binding PDA, a Variant-C caller check, a proportional seize hook)
  maps onto 0.4, but every line is rewritten. The caller check becomes `input.from ==
  Actor(engine_config, engine_program)`. The seize becomes sync messages to the position and token actors.
  There are no return values, so the engine cannot read the seized amount back from a call. [I]

## 5. lez_core (logos-execution-zone-module)

- Our pin is 0.4.1 (`acf0cd50`, LEZ v0.2.x). `main` = 0.5.1 (`fdd6a75a`), on LEZ **v0.3.1** (flake.nix).
  v0.3.2's release notes say "lez_core 0.5.1 … stay correct". [C]
- **0.4:** open PR **#72** "feat!: Sequencer FFI adaptation" (branch `Pravdyvy/sequencer-ffi-adaptation`,
  head `9e3d774c`, updated 2026-10-30, metadata version **0.6.0**) pins `v0.4.0-rc1`. It renames shards to
  actor states and `ProgramWithDependencies` to `ProgramCatalog`, frees memory through `primitives_free_*`,
  and **wallet open/create now requires a running sequencer**. [C]
- `send_generic_public_transaction`, from our pin to the 0.4 PR: [C]
  - 0.4.1: `(account_ids, signing_requirements, instruction, program_id_hex)`
  - 0.5.1: `(…, instruction, program_id_hex, payer_account_id_hex, shard_program_account_ids_hex)`
  - 0.6.0 (PR #72): `(account_ids, uint64 root_mention, signing_requirements, message, payer_account_id_hex,
    actor_state_program_account_ids_hex)`. The program ID is gone: the root is an index into the mentions.
- `poll_transaction_status` exists since 0.5.x. Affected code: `modules/auction_engine/src/lez_args.h`,
  `auction_engine_impl.cpp:270`, the mocked `tests/logos_sdk.h` and `harness.h`, and the module's flake pin.
- [3P] vpavlin's playground skipped lez_core for 0.4 and links LEZ `lez/core_ffi` directly. That is a
  fallback if #72 lags.

Rough total: 8-12 weeks of work. On the critical path it is gated by three upstream items: the testnet, SPEL
and lez-programs. [I]

**Riskiest unknowns**
1. U1 (SPEL) cannot be satisfied for 0.4 today. The SPEL v0.3 port targets a model that 0.4 has already
   replaced. Ask Logos whether a hand-maintained SPEL-schema IDL is acceptable, as #237 does.
2. The engine's atomic multi-account settlement under "no return values". F2 bids and F3 settlement need
   reply-message patterns. The whole-gas-limit cost of a revert changes keeper economics and the SDK's
   pre-checks.
3. The host stablecoin's 0.4 port: when, and which instruction and account layout. The `generate_debt`
   oracle drop, the new enum variant and #445 already change our seams on v0.2.5.
4. rc1 → 0.4.0 churn: #956, #957 and #974 are open, and #985 forced a genesis restart a day before rc1.
5. Standalone mode does not finalize, so no events. The ADR-043 "indexer and events replace the block scan"
   plan from the v0.3 doc does not work in standalone CI. Keep the block scan. [3P/I]

- "SPEL main targets v0.2.5-rc2": still true. The v0.3 work is on the fork (`0x-r4bbit/spel`), with no 0.4
  work.
- "lez-programs main is 64c01210": now `6674d783` on v0.2.5-rc2, with breaking stablecoin changes.
- "rfp #214 open": merged 2026-10-22.
