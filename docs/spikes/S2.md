# S2: Host authentication of the engine (`caller_program_id` vs PDA signer vs both)

Status per brief step: 1 DONE, 2 DONE (3 variants x 4 tests, all pass, cycles measured). Fix round 1 added a fifth attack (authorisation laundering) that **overturns the original decision: the decision is now variant C**. The shared workspace also covers S3 and S7 (see S3.md, S7.md).

## Question

How does the host program (the stablecoin side, here stood in by `callee`) authenticate that `liquidate_position` / `engine_freeze_new_debt` was invoked by the auction engine and nobody else?

- Variant A: `ctx.caller_program_id == stored engine program id`.
- Variant B: the stored engine authority PDA is an account that is authorised in the call (the engine authorises it with `ChainedCall::with_pda_seeds`).
- Variant C: both.

Decision rule from the brief: choose the cheapest variant that passes all four tests; if both A and B pass, prefer B (upstream fit) unless A is more than 20% cheaper. **This rule was superseded** (see Decision): its four tests were an incomplete attack set, and the spec's actual requirement is that only the engine can invoke the hook.

Programs:

- `callee`: `guarded_a`, `guarded_b`, `guarded_c`. Each takes `config` (a PDA of `callee`, seed `CALLEE_CFG`, owner-checked, holds `engine_program_id` and `engine_authority`), `authority`, `bystander`. A asserts `ctx.caller_program_id == config.engine_program_id`; B asserts `authority.account_id == config.engine_authority && authority.is_authorized`; C does both. Nothing is stored.
- `caller` (the engine stand-in): `call_guarded(variant, callee_program_id)`, accounts `config`, `authority` (`#[account(pda = literal("ENGINE_AUTH"))]`), `user` (signer). For B and C it sets `authority.is_authorized = true` and chains with `.with_pda_seeds(vec![ENGINE_AUTH seed])`; for A it chains with the authority unauthorised and no seeds.
- `impostor`: `attack(callee_program_id, variant, mode)` chains to `callee.guarded_*`. Mode 0 forges `is_authorized = true` on the engine authority account without seeds; mode 1 forges the flag and also passes seeds `ENGINE_AUTH`, which derive the wrong address under the impostor's id; mode 2 passes the impostor's own `ENGINE_AUTH` PDA (legitimately authorised under its own seeds).

Deviation from the brief, deliberate: the brief's `guarded(expected_caller: [u8;32])` takes the expected value as an argument. An argument chosen by whoever builds the call is not a guard (the impostor would pass its own id), so the expected values are read from a stored `CalleeConfig` account ("stored_engine_program_id", "stored_engine_authority_pda" in the brief's own wording). The config account is inserted into the test state with `force_insert_account`; no initialiser instruction was written, so "how the config is set and who may rotate it" is not tested.

### Fifth attack: authorisation laundering (fix round 1)

lee v0.2.4 propagates authorisation down the call chain: `validated_state_diff/mod.rs:262-290` unions the caller's authorised set with every `is_authorized` pre-state of the program that just ran, "so that authorization is monotonically growing: once an account is authorized at any point in the chain it remains authorized for all subsequent calls". So if the engine chains with the `ENGINE_AUTH` seeds to any program X, X can chain to `callee.guarded_*` with the PDA flagged authorised and lee accepts it (no seeds needed, nothing forged). The spike's `caller.call_guarded` takes `callee_program_id` from the caller, so any signer can make the engine authorise the PDA for an attacker program; `caller.call_untrusted` reproduces exactly that flaw on purpose (engine -> `impostor.launder` -> `callee.guarded_*`).

| Variant | Laundered call (engine -> X -> callee) | Evidence |
|---|---|---|
| A | rejected: `guard A: caller program is not the engine program` (immediate caller is X) | `laundering_variant_a_rejects` |
| B | **accepted** (`Ok(())`): the bypass works | `laundering_variant_b_accepts_the_bypass` |
| C | rejected: `guard A: ...` | `laundering_variant_c_rejects` |

A and C hold because `caller_program_id` is the immediate caller and lee enforces it per call (`MismatchedCallerProgramId`, `validated_state_diff/mod.rs:184-191`). B's guarantee, stated correctly: "the engine authority PDA is authorised somewhere in the chain that led here", NOT "the engine is the caller". It is only as strong as the engine's discipline never to authorise the PDA for a program it does not fully trust.

## Decision

**Variant C (A and B together).** Original outcome was B (all three passed the four brief tests; A only 1.35% cheaper). The laundering test above shows B alone is bypassable, so the brief's rule ("cheapest variant passing all four tests") was built on an incomplete attack set and is superseded by the spec's requirement that only the engine can invoke the hook. C costs 372,601 cycles against B's 372,316 (+285, +0.08%) and A's 367,354 (+5,247, +1.43%); the cost difference is negligible.

Defence-in-depth invariants for Plan 2 (C does not remove the need for them):

1. The engine never authorises `ENGINE_AUTH` for any program other than the stored host program id (no caller-supplied program ids; the spike's `call_guarded` and `call_untrusted` are the anti-pattern).
2. The host never chains to an untrusted or user-chosen program while the engine authority is authorised in its call.

Remaining caveats (also in ADR-019):

- **Zero ids (M1).** SPEL sets `ctx.caller_program_id` to all zeros for a top-level call (`spel-framework-core/src/context.rs:30-33`), so A and C accept a direct call if the stored `engine_program_id` is zero or uninitialised. The config initialiser must reject zero program ids and zero authorities (Plan 2 test).
- **Private path (I1), untested.** In the privacy-preserving circuit, `authorized_accounts` is one set for the whole transaction (`lee/privacy_preserving_circuit/src/execution_state.rs:54`, `601-608`): after the first authorisation every later call, including sibling calls, sees the account as authorised, so the laundering scope is wider than on the public path. Forgery is still blocked (`output.rs:38`, `circuit/mod.rs:420-433`, `execution_state.rs:285-305`). A PDA first seen inside a chained call is not seed-checked in the Vacant branch, so the engine must list the authority in its own accounts. `caller_program_id` IS enforced in the circuit per call: `execution_state.rs:164-170` asserts `program_output.caller_program_id == caller_program_id` ("does not match actual caller"), the comment there citing spoofing. So variant A/C's immediate-caller check also holds on the private path, which is why C covers it; this was read from source and no private-path test was run. Open item for Plan 2: write that test.
- A and C failed tests (4) and (3) on the `caller_program_id` check; only B exercises the PDA path in those tests.
- Both A and B bind to the engine ImageID (the PDA derives from the program id): a second or upgraded engine build needs its own stored config; update path untested.
- Upstream fit (M5): the stablecoin's admin and freeze checks are plain `is_authorized` assertions: `lez-programs/programs/stablecoin/src/checks.rs:109` ("Admin authorization is missing") and `src/freeze.rs:58` (freeze authority authorised and id matching). Variant B mirrors those. Note they carry the same laundering property whenever the authority is a PDA.
- Not tested: config creation and rotation, a real sequencer run, proving. Cycles are executor cycles from natively built guests.
