# S2: Host authentication of the engine (`caller_program_id` vs PDA signer vs both)

Status per brief step: 1 DONE, 2 DONE (3 variants x 4 tests, all pass, cycles measured), shared workspace also covers S3 and S7 (see S3.md, S7.md).

## Question

How does the host program (the stablecoin side, here stood in by `callee`) authenticate that `liquidate_position` / `engine_freeze_new_debt` was invoked by the auction engine and nobody else?

- Variant A: `ctx.caller_program_id == stored engine program id`.
- Variant B: the stored engine authority PDA is an account that is authorised in the call (the engine authorises it with `ChainedCall::with_pda_seeds`).
- Variant C: both.

Decision rule from the brief: choose the cheapest variant that passes all four tests; if both A and B pass, prefer B (it mirrors the stablecoin's admin/freeze checks, so it is the upstream fit) unless A is more than 20% cheaper.

Programs:

- `callee`: `guarded_a`, `guarded_b`, `guarded_c`. Each takes `config` (a PDA of `callee`, seed `CALLEE_CFG`, owner-checked, holds `engine_program_id` and `engine_authority`), `authority`, `bystander`. A asserts `ctx.caller_program_id == config.engine_program_id`; B asserts `authority.account_id == config.engine_authority && authority.is_authorized`; C does both. Nothing is stored.
- `caller` (the engine stand-in): `call_guarded(variant, callee_program_id)`, accounts `config`, `authority` (`#[account(pda = literal("ENGINE_AUTH"))]`), `user` (signer). For B and C it sets `authority.is_authorized = true` and chains with `.with_pda_seeds(vec![ENGINE_AUTH seed])`; for A it chains with the authority unauthorised and no seeds.
- `impostor`: `attack(callee_program_id, variant, mode)` chains to `callee.guarded_*`. Mode 0 forges `is_authorized = true` on the engine authority account without seeds; mode 1 forges the flag and also passes seeds `ENGINE_AUTH`, which derive the wrong address under the impostor's id; mode 2 passes the impostor's own `ENGINE_AUTH` PDA (legitimately authorised under its own seeds).

Deviation from the brief, deliberate: the brief's `guarded(expected_caller: [u8;32])` takes the expected value as an argument. An argument chosen by whoever builds the call is not a guard (the impostor would pass its own id), so the expected values are read from a stored `CalleeConfig` account ("stored_engine_program_id", "stored_engine_authority_pda" in the brief's own wording). The config account is inserted into the test state with `force_insert_account`; no initialiser instruction was written, so "how the config is set and who may rotate it" is not tested.

## Problems hit

- A rustc ICE (`slice index starts at 20 but ends at 18`, in `annotate_snippets` while rendering a lint) aborted the guest build the first time and again after a touch-rebuild. The cause was an unused-import warning (`AUCTION_TAG`) in `caller.rs`; removing the warning made the guest build cleanly (`rustc-ice-*.txt` files were deleted and are not in the repo). Keep guest sources warning-free.
- A first build attempt was cut off by the tool's 10-minute background limit (not a build failure); it was restarted with `setsid nohup`.
- Nothing needed a pin change. The shell quirk that `D=~/path` style arguments are mangled when passed through Git Bash to `wsl` was worked around by using `$HOME` inside `bash -lc`.

## Decision

**Variant B (engine authority PDA must be authorised in the call).** All three variants pass all four tests; A is the cheapest but only by 1.35%, so the brief's rule (prefer B unless A is >20% cheaper) selects B, which also mirrors the stablecoin's existing admin/freeze account checks.

What the evidence does and does not show (these caveats are repeated in ADR-019):

- The B guard in the guest does not by itself reject a forged `is_authorized` flag: modes 0 and 1 passed the guest and were stopped by lee's post-execution authorisation check (`InvalidAccountAuthorization`). B is therefore only as strong as that lee rule. A's check is enforced against `caller_program_id`, which lee also verifies (`MismatchedCallerProgramId`).
- A and C fail test (4) on the `caller_program_id` check, so test (4) only exercises the PDA path for B.
- Both A and B bind to the engine's ImageID (a PDA is derived from the program id). A second engine build or an upgraded image changes both values, so the stored config must be updated per instance. Not tested: the update path.
- Not tested: `callee` config creation and rotation, a real sequencer run, or proving. Cycles are executor cycles from natively built guests.
- ADR: see ADR-019 in `docs/design-log.md`.
