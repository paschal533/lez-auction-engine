# S3: Creating a PDA on first use with an argument-derived seed

Status per brief step: 1 DONE (shared workspace, see S2.md), 3 DONE (all four tests plus extras pass, cycles measured).

## Question

Can a SPEL program create `["LIQREC", config, position]` (the `LiquidationRecord`) on first use with `Claim::Pda`, and derive auction PDAs `["AUCTION", config, position, nonce]` whose seeds come from instruction arguments? What exact attribute syntax works at the pinned SPEL rev, and does the off-chain derivation match the on-chain one?

## Environment

Identical to S2 (see `docs/spikes/S2.md`): WSL-native workspace `~/lez-spikes/s2_s3_s7/` copied as sources to `spikes/s2_s3_s7/`; logos-execution-zone `v0.2.4` (`47eba256`), SPEL `1ef0500f`, risc0-zkvm `=3.0.5`; tests are in-process `V03State` tests (`spike_tests/tests/s3_pda.rs`).

The programs under test are in `caller` (`methods/guest/src/bin/caller.rs`):

- `open_record(position)`: creates `["LIQREC", config, position]` if the account is still default (`Claim::Pda`, claim-if-default), then `count += 1`. Literal reading of the brief.
- `open_auction(position, nonce)`: first-use path. Creates the record if absent, asserts `nonce == record.count` (count before the increment), creates `["AUCTION", config, position, nonce]`, `count += 1`. All claims are built explicitly.
- `open_auction_existing(position, nonce)`: record must already exist; the auction claim is the one the SPEL macro generates from `#[account(init, pda = [...])]`.

The brief's wording ("creates the record if uninitialised and increments a count"; "asserts `nonce == record.count`, creates the auction, increments the count") is ambiguous about whether `open_record` and `open_auction` both bump the count and whether `open_auction` creates the record. I implemented all three readings (above) and tested each; the engine design should pick one counter owner (see Decision).

## The attribute syntax that worked

Validation and seeds (macro `spel-framework-macros` at `1ef0500f`; syntax read from `parse_pda_expr`, confirmed by compiling and running):

```rust
// record: exists or not; address is checked, claim is done by hand
#[account(mut, pda = [literal("LIQREC"), account("config"), arg("position")])]
record: AccountWithMetadata,

// auction: must be uninitialised; macro validates the address AND generates the claim
#[account(init, pda = [literal("AUCTION"), account("config"), arg("position"), arg("nonce")])]
auction: AccountWithMetadata,
...
position: [u8; 32],
nonce: u64,
```

Seed kinds and encodings (all verified by the off-chain-equals-on-chain test):

| Seed | Meaning |
|---|---|
| `literal("X")` (also `const("X")`, both accepted at this rev) | UTF-8 bytes, zero-padded to 32, at most 32 bytes |
| `account("name")` | the 32-byte id of the instruction account called `name` (the name must be a parameter of the same instruction) |
| `arg("name")` with `[u8;32]` | the bytes as they are |
| `arg("name")` with `u64` | little-endian bytes, zero-padded to 32 (`ToSeed for u64`); `u32`, `String`, `&str` also implemented |
| several seeds | `SHA-256(seed_1 || seed_2 || ...)` (each part is 32 bytes); a single seed is used as is |

The PDA id is `AccountId::for_public_pda(program_id, PdaSeed::new(combined))`.

Claims:

- `#[account(init, pda = [...])]` plus the **two-segment** call `SpelOutput::execute(vec![ident, ident, ...], chained_calls)` makes the macro rewrite the call to `execute_with_claims` with `Claim::Pda(combined seed)` for the `init` account, `ClaimedIfDefault(Authorized)` for `signer` accounts and no claim for `mut`/plain accounts (`open_auction_existing`). The rewrite only happens for the exact path `SpelOutput::execute` and a `vec![idents]` argument.
- The three-segment path `spel_framework::SpelOutput::execute(vec![AccountPostState..], calls)` is not rewritten; the program supplies the post states itself (the token program's style). This is how create-if-absent is done:

```rust
let claim = Claim::Pda(PdaSeed::new(combine_seeds(&[&seed_from_str("LIQREC"), config.account_id.value(), &position])));
AccountPostState::new_claimed_if_default(record_account, claim)   // claims only while the account is still default
AccountPostState::new_claimed(auction.account, Claim::Pda(auction_seed(&config.account_id, &position, nonce)))
```

- `#[account(init, ...)]` makes the generated validation fail with `AccountAlreadyInitialized { account_index }` when the account is not default, so `init` cannot express "create if absent"; use `mut` + `pda = [...]` for the address check and `new_claimed_if_default` for the claim.
- A wrong account passed for a `pda = [...]` slot fails with `PdaMismatch { account_name, expected, actual }` (tested).
- The claim needs no signature from the PDA: lee only checks that the claimed PDA derives from the claiming program and the seed (`MismatchedPdaClaim` otherwise).

## Problems hit

- Two of my own expected-error strings were wrong on the first run (the replay is rejected by `AccountAlreadyInitialized`, not by the nonce assertion); the tests were corrected, no program change.
- The rustc ICE described in S2.md (unused import warning in the guest) applies to this workspace too.
- The brief's "second call with the same nonce fails" is satisfied, but note the reason: the auction PDA for that nonce already exists, which makes the on-chain `nonce == count` assertion a second line of defence rather than the first.

## Decision

SPEL at the pinned rev supports what the engine needs: multi-seed PDAs mixing a literal, another account's id and instruction arguments (including `u64` nonces), validated by the macro; claims either macro-generated (`init`) or explicit (`new_claimed_if_default` for create-if-absent). Plan 2 should use `mut` + `pda = [..]` + `new_claimed_if_default` for `LiquidationRecord` and `init` + `pda = [..]` (macro claim, or explicit when it is created in the same instruction as the record) for each auction, and derive both off-chain with the same `combine_seeds` rule (the helper in `spikes/s2_s3_s7/core/src/lib.rs` is a working reference).

Counter ownership (controller ruling, fix round 1): the per-position `count` is incremented **only by auction creation**. This is the spike's `open_auction` reading (create-if-absent of the record inside the auction instruction, `nonce == count`, `count += 1`); the standalone `open_record` that also bumps `count` is the rejected shared-counter design. Hazard: a permissionless `open_record` lets anyone bump `count`, front-running and griefing auction creation (every honest `open_auction` with the old nonce then fails). `open_record` stays in the spike only as the minimal create-if-absent demonstration. Plan 2 removes the standalone bump (record creation happens inside `liquidate`/`open_auction`), and must validate `config` (the spike uses a plain default account).

Caveats (repeated in ADR-020):

- Only in-process `V03State` execution was tested. Not tested: a real sequencer submit, the `spel` CLI with arg-seeded PDAs, or generated IDL for the `[u8;32]`/`u64` args.
- Count ownership was resolved by the controller ruling above (auction creation only).
- `config` is a plain default account in these tests (not an engine config PDA), and `open_*` are permissionless for any signer; access control is the engine's job.
- Cycles are executor cycles from natively built guests, not proving cost.
- ADR: see ADR-020 in `docs/design-log.md`.
