# S4: Discount curve shape (cost of the core operations in the zkVM)

Status: DONE. Numbers are **dev-mode executor cycles, not proving cost** (see Environment).

## Question

Piecewise-linear vs exponential vs stairstep discount curve (spec §13, "Cycles + accuracy"). The brief's rule: keep the piecewise-linear schedule unless the exponential variant is within 10% of its cycles **and** reviewers would care.

## Environment

- Same as S1/S2 (see `docs/spikes/S1.md`): WSL distro `Ubuntu-20.04` (Ubuntu 24.04.4), rustc 1.94.0, risc0 `risc0-zkvm =3.0.5`, rzup `rust 1.94.1`, `r0vm 3.0.5`; `~/lez-spikes/s1/env.sh` sourced for every build. No sudo, Docker not used (the guest is built by `risc0-build` with the local rzup toolchain, so the ELF is not the Docker-built image).
- Built WSL-natively at `~/lez-spikes/s4_s6/` (controller ruling: the repo is on `/mnt/c`). **How the guest reaches `auction_core`:** the WSL tree mirrors the repo layout. `git archive HEAD Cargo.toml rust-toolchain.toml crates/auction_core` at **`627bba4`** was extracted to `~/lez-spikes/s4_s6/`, and the spike lives at `~/lez-spikes/s4_s6/spikes/s4_s6/`. The guest therefore uses the same relative path in WSL and in the repo: `auction_core = { path = "../../../../crates/auction_core" }`. Reasons for a copy rather than `/mnt/c/...`: the root manifest is needed for `edition.workspace`/`license.workspace` inheritance, and reading sources over 9p is slow. `auction_core` was not modified and gained no dependency (the serialiser `borsh` is in the guest's `Cargo.toml` only).
- Sources only are copied into this repo at `spikes/s4_s6/` (no `target/`). Cycle lines are in `spikes/s4_s6/logs/cycles-excerpt.log`.
- **Which number is reported:** `session.cycles()` from `default_executor().execute(..)`. In risc0 3.0.5 this is the sum of per-segment **user cycles**, with no po2 padding, paging or continuation overhead (`SessionInfo::cycles`, `host/api/mod.rs`). The host also prints each segment's `(po2, cycles)`. These are executor cycles of a natively built guest, **not** proving cost and not the Docker-built image.

## Method

`spikes/s4_s6/methods/guest/src/bin/bench.rs` is one guest. The host sends `[op, reps, ...]`; the guest builds its fixtures, then runs operation `op` `reps` times with a per-repetition varied input (`black_box`, so nothing is hoisted) and commits a checksum. The host runs every case with `reps = 1` and `reps = 11`:

- **gross** = cycles(reps = 1): includes the guest start-up, input read and fixture construction (an empty `noop` costs 53,703);
- **marginal per operation** = (cycles(11) − cycles(1)) / 10: the cost of one more execution of the operation. **This is the number to use.**

Operations (all call the real `auction_core` code): `mul_div_floor` (`u128::MAX − i`, `u128::MAX − 1`, `u128::MAX`: full 128-bit divisor and non-zero high word; and small operands), `Schedule::discount_ray` for 2 points (`rai_default`) and for 8 points (evaluated in the last segment, so all windows are scanned), `quote_liquidation`, `quote_bid` + `apply_bid` (non-final fill), `take_debt` (partial take), and the exponential variant `RAY · (1 − r)^t`: binary exponentiation in RAY fixed point with `mul_div_floor` (`r = RAY/20 000` per second, `t` in seconds up to 7 200). Checksums in the log show every case took its `Ok` path.

The exponential cost is `(squarings + multiplications) × ≈10.36k`, exactly the `mul_div_floor` price (16 → 165,779; 24 → 248,565; 23 → 238,212; 9 → 93,309). Segments: every `reps = 1` run fits one segment (po2 17 to 19); the 11-rep exponential runs split into 2 to 3 po2-20 segments (visible in the log). Because `cycles()` is user cycles, the splitting does not distort the marginals.

## Decision rule, with the arithmetic

The rule asks whether the exponential variant is within 10% of the piecewise cycles, i.e. at most 1.10 × 8,889 = **9,778** cycles (8 points: 1.10 × 8,936 = 9,830).

| Variant | Cycles | Ratio to piecewise (2 points) | Within 10%? |
|---|---:|---:|---|
| exponential `t = 7 200` | 165,779 | 18.65× (+1,765%) | No |
| exponential worst case `t = 6 143` | 248,565 | 27.96× (+2,696%) | No |
| exponential vs the 8-point schedule (8,936) | 165,779 / 248,565 | 18.55× / 27.82× | No |

The first condition fails by more than an order of magnitude, so the "and reviewers would care" condition is not needed: **keep the piecewise-linear schedule.**

In context: replacing `discount_ray` inside `quote_bid` (19,802 total) by the exponential variant would give 19,802 − 8,889 + 165,779 = **176,692** (8.9×) at `t = 7 200`, and 19,802 − 8,889 + 248,565 = **259,478** (13.1×) in the worst case. Against the modelled full bid chain of about 0.9 M cycles (see S6) that is +17% to +27% on every bid, plus the same on every `take_debt`/surplus take, for a curve nobody asked for.

## Accuracy and stairstep (analysis, not measured)

- Piecewise-linear integer arithmetic is one `mul_div_floor`, rounded down, so the discount is never overstated against the protocol and the error is below one RAY unit per evaluation. This is also the shape already covered by the property tests, the Kani proofs and the differential model.
- The exponential variant floors every one of up to 24 multiplications; each floor lowers `(1 − r)^t` slightly, so the resulting discount is slightly **too high** (it favours the bidder), by at most about 24 RAY units (about 2.4e-26 relative): negligible, but it is the wrong rounding direction for a protocol-favouring rule, and `r` is a per-second rate that would need its own validation (cap at 30%, monotonicity, ranges).
- Stairstep was not run (the brief's operation list does not include it). It is no more expensive than piecewise-linear, since it needs no `mul_div`, and a piecewise schedule with closely spaced points reproduces it without a new code path.

## Problems hit

- Git Bash mangles `/mnt/...` arguments passed to `wsl` (it rewrites them to `C:/Program Files/Git/mnt/...`); use `MSYS_NO_PATHCONV=1` or keep paths inside `bash -lc "..."`. Nothing else; no pin changes.

## Decision

Keep the piecewise-linear `Schedule` (up to 8 points). ADR-022 in `docs/design-log.md`.
