# S6: Accounting update timing (per bid or at chain end)

Status: DONE. Numbers are **dev-mode executor cycles, not proving cost**.

## Question

Does `bid` update `Accounting` on every bid, or only at chain end? The brief's rule: prefer per-bid updates (simpler R6 proof) **unless they add more than 5% of a bid's cycles**. The sequencer executes transactions one at a time, so there is no write-conflict cost to weigh.

## Environment and method

Identical to S4 (`docs/spikes/S4.md`): same guest, same host, same WSL workspace `~/lez-spikes/s4_s6/` with `auction_core` copied at `627bba4`; `session.cycles()` = user cycles of the executor, marginal cost = (cycles(11 reps) − cycles(1 rep)) / 10. Evidence: `spikes/s4_s6/logs/cycles-excerpt.log`.

What was measured, using the **current** `Accounting` struct (all ten fields: seven `u128`, two `u64`, one `bool`; **129 bytes** in borsh):

1. `accounting_borsh_serialise`: borsh-encode the whole struct (a `borsh` mirror struct `AccountingWire` in the **guest's** `Cargo.toml`/code; `auction_core` stays dependency-free).
2. `accounting_rmw_per_bid`: the whole per-bid update: borsh-decode the stored bytes, `Accounting::record_bid(&fill)`, borsh-encode the result.
3. **The cost of one more account in the instruction.** Serialising a struct is the small part. An extra account in the write set must also be read from the input and echoed in the output. Measured with the **real** `lee_core` v0.2.4 types (`AccountWithMetadata`, `AccountPostState`, `Account` with 129 bytes of data), `n` accounts per run:
   - `in_only`: the guest reads `n` pre-states;
   - `in_pre_echo_post`: the guest reads `n` pre-states, then commits them back (`ProgramOutput` echoes the pre-states) and commits `n` post-states. This is the shape of an account that is part of a program's write set.

   Note on serde: `Account.data` serialises as a `Vec<u8>`, i.e. one 32-bit word per byte, and `AccountId` serialises through `SerializeDisplay` (a string), so accounts are expensive to move through the guest boundary.

## Raw numbers

| Measurement | Cycles |
|---|---:|
| borsh serialise of `Accounting` | 691 |
| **per-bid read-modify-write** (decode + `record_bid` + encode) | **1,530** |
| input only, one extra 129-byte account: n = 1 / n = 3 (n = 0 baseline 53,689) | 36,776 / 36,741 per account |
| input + echo + post-state, one extra account: n = 1 / n = 3 (n = 0 baseline 54,060) | 93,392 / 93,374 per account |
| `quote_bid` + `apply_bid` (S4) | 19,802 |

Per-bid overhead of updating `Accounting` on every bid = account I/O 93,374 + read-modify-write 1,530 = **94,904 cycles**.

## Denominator: what is "a bid's cycles"?

There is no engine program yet, so a full bid cannot be run. The real chain per spec §5.6 is: the engine `bid` instruction (its own work: pause observation, oracle read, clock, auction and vault updates) chaining **Burn** (debt part), **Transfer** (penalty to the SurplusBuffer) and **Transfer** (collateral out), i.e. **three token executions** plus the engine execution. Three estimates, all built from S1 measurements:

| Denominator | Cycles | Extra 94,904 as a share |
|---|---:|---:|
| (a) core-only bid (`quote_bid` + `apply_bid`) | 19,802 | 479% |
| (b) first model: S1's `withdraw_collateral` execution (626,902) as a proxy for the engine instruction, plus two `Token::Transfer` executions (2 x 133,827 = 267,654) | 894,556 | 10.61% |
| (c) (b) plus a third token execution (+133,827, the burn leg of the real chain) | 1,028,383 | 9.23% |
| (d) account-count estimate: about 8 accounts at about 93k each plus core and start-up (about 0.8 M) plus two transfers | about 1.07 M | 8.9% |

(a) overstates the share, since a bid is never only the core. (b) **under-counts** the bid: it has one token execution fewer than the real chain and no allowance for oracle or pause work beyond what `withdraw_collateral` happens to do, so **10.6% is an upper estimate**, not a central one. (c) and (d) are closer to spec §5.6. **The decision holds across all of them:** every full-bid estimate is above 5% (8.9% to 10.6%). **Break-even:** the extra cost falls under 5% only if a full bid costs more than 94,904 / 0.05 = **1,898,080** cycles, about 1.8x to 2.1x the estimates. The real bid is to be re-measured in Plan 3 (`CYCLES.md`).

Caveats on the 94,904: it slightly over-attributes, because the measured post-state commits a full `Account` clone (an engine would commit the same, but the figure includes the whole account including unchanged fields), and it is single-program executor user cycles (no chained-call, host-side or proving overhead).

## Decision rule, with the arithmetic

Per-bid updates add **8.9% to 10.6%** of a bid (10.6% is an upper estimate; 9.2% with the third token execution), which is more than 5% under every full-bid denominator considered. **Update `Accounting` only at chain end.**

Why this is safe:

- `record_bid` is purely additive: it adds `debt_part` to `total_debt_burned` and `penalty_part` to `total_penalty_collected`. The `Auction` already carries the running sums (`debt_raised`, `penalty_raised`), and `raised() = debt_raised + penalty_raised` is what the existing property test checks against the two counters (`total_debt_burned + total_penalty_collected == a.raised()`). Applying `record_bid` once at chain end with `debt_part = auction.debt_raised` and `penalty_part = auction.penalty_raised` gives the same totals as applying it to every fill. No core change is required for this (a named helper would be convenient; see Consequences).
- Nothing in the core reads those two counters to make a decision. `unbacked_debt`, `total_shortfall_booked` and `debt_on_auction` are not touched by bids; the chain end already writes `Accounting` (`record_chain_end`, shortfall), so the final bid pays for the write anyway.
- The supply invariant of spec §5.8 (`stablecoin_supply ≤ Σ position debt + Σ live (debt_principal − debt_raised) + unbacked_debt`) does not use the two counters, so the R6 proof is not affected by when they are written; only the statement "counter equals Σ raised" holds at chain end instead of after every bid.
- Concurrency is not a cost either way (sequential sequencer). Qualitatively, non-final bids of different auctions then share no `Accounting` account, which tightens the R3 isolation statement (spec §5.4: a non-final bid writes its auction, vault, buffer and holdings only).

## Consequences for Plan 2

1. `bid` takes the `Accounting` account only when the fill ends the auction (or a separate chain-end path writes it); non-final bids do not list it.
2. **Every chain-end path must apply the cumulative update** (`record_bid` with the auction's `debt_raised`/`penalty_raised`, plus `record_chain_end`), or counters are silently dropped. The paths: (i) the settling `bid` (`apply_bid` returns `Some(ChainEnd)`; this includes a final-fill that ends the auction by exhausting the lot or reaching the target); (ii) `settle_empty` (lot already 0, permissionless): the raised amounts may be non-zero from earlier bids, so the cumulative `record_bid` is still needed, and `record_chain_end` books the shortfall. Any future settlement path must do the same. A small `Accounting::record_settled(&Auction)` helper is advisable in Plan 2 so no program builds a synthetic `BidFill` and no path forgets the fold.
3. The property test `total_debt_burned + total_penalty_collected == raised` in `tests/invariants.rs` should be restated for this flow (it holds after the chain end of each auction; for in-flight auctions the amounts live in the `Auction`).
4. Any off-chain dashboard that shows these totals must add `raised()` of live auctions, or accept that they lag until chain end.
5. Re-measure with the real engine instruction in Plan 3 (`CYCLES.md`); if a full bid ever costs more than about 1.9 M cycles the rule flips and the switch is trivial (add the account to `bid` and call `record_bid` per fill).
6. Whether a bid ends the auction is decided at execution time (price and t_eff move between signing and inclusion), while LEZ needs the account list at signing. A bid signed without the chain-end accounts (Accounting, CollateralConfig/EngineConfig for the reservation release) that turns out to end the auction must revert with a distinct error so the client re-quotes, or Plan 2 adds a permissionless finalize path. Clients list the accounts whenever coin_in_max >= remaining or the quoted fill is near the lot. If most bids end up listing Accounting, re-evaluate S6: its 94,904-cycle saving assumes non-final bids omit the account.

## Caveats

- The denominators are modelled from S1 numbers and an account-count estimate, not from a running engine. The threshold test (5%) is not close under any estimate (8.9% to 10.6%), but they are estimates.
- 129-byte account data was used for the extra account; real `Accounting` data is exactly 129 bytes (borsh). The per-account I/O cost grows with data length (one word per byte).
- Executor cycles of a natively built guest; not proving cost and not the Docker-built image.

## Decision

`Accounting` is updated only at chain end. ADR-023 in `docs/design-log.md`.
