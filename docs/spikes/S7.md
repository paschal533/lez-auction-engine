# S7: Mock protocol token minted from an engine PDA, then burned

Status per brief step: 1 DONE (shared workspace, see S2.md), 4 DONE (mint by PDA, mint by user key fails, burn by holder, cycles recorded).

## Question

Can a token definition whose mint authority is a PDA of the engine program be minted by the engine through a chained `Token::MintWithAuthority` (with PDA seeds), can a user key not mint, and can the holder burn through a chained `Token::Burn`? What does each cost in cycles?

## Environment

Identical to S2 (`docs/spikes/S2.md`). The token program is the lez-programs guest at the pinned rev `64c01210`, built natively through the `token-methods` git dependency (`TOKEN_ELF`, `TOKEN_ID`), deployed into the in-process `V03State` next to `caller`. Model followed: `lez-programs/programs/token_mint_authority` (`faucet_mint.rs`): definition `TokenDefinition::Fungible { authority: Some(<PDA>) }`, mint through `Token::MintWithAuthority` with the PDA marked authorised and passed via `.with_pda_seeds`.

`caller` additions (`methods/guest/src/bin/caller.rs`):

- `mint_to(amount_to_mint)`: accounts `operator` (signer), `definition` (mut), `holder_holding` (mut), `mint_authority` (`#[account(pda = literal("MINT_AUTH"))]`). Chains `Token::MintWithAuthority` with `[definition, holder_holding, mint_authority(authorised)]` and seed `MINT_AUTH`.
- `burn_from(amount_to_burn)`: accounts `definition` (mut), `holder_holding` (mut, signer). Chains `Token::Burn` with `[definition, holder_holding]`; the holding is authorised because the holder signed the top-level transaction.

Fixture: the definition (authority = `named_pda(caller, "MINT_AUTH")`) and the holder's already initialised holding are inserted with `force_insert_account`, as the lez-programs token tests do.

## Results

All 4 S7 tests pass in the final run.

| Test | Result |
|---|---|
| mint by the PDA: `caller.mint_to(1000e18)` leaves the holder balance and total supply at `1000e18`; a second mint of `5e18` stacks to `1005e18` | pass |
| mint by a user key fails, three ways: (a) user calls `Token::MintWithAuthority` directly with their own key as authority: `Mint authority check failed: signer is not the current authority`; (b) the PDA listed as authority in a direct call: `Account 'authority_account' (index 2) must be a signer`; (c) `Token::Mint` (self-authority) on the definition: `Account 'definition_account' (index 0) must be a signer`. Balance and supply stay 0 | pass |
| burn by the holder: after minting `1000e18`, `caller.burn_from(400e18)` signed by the holder leaves balance and supply at `600e18` | pass |
| burn without the holder's signature fails: `Account 'holder_holding' (index 1) must be a signer`; balance and supply unchanged | pass |

Cycles (2 program executions per transaction, of the 11 allowed; executor cycles, same method as S2):

|---|---|---|---|
| `mint_to` (chained `MintWithAuthority`) | 285,927 | 179,913 (179,911 for the second mint) | **465,840** |

## Problems hit

- One expected-error string in my test was wrong on the first run (the PDA-listed-but-unauthorised case is rejected by the token program's SPEL `signer` check, not by a custom assertion); the test was corrected, no program change.
- The rustc ICE from an unused-import warning described in S2.md applies here too.

## Decision

Mint from an engine PDA works exactly like the faucet's flow: set the definition's `mint_authority` to the engine's PDA, chain `MintWithAuthority` with the PDA seed. A user key cannot mint. A holder-authorised chained burn works. Costs: about 466k cycles to mint and 331k to burn, 2 executions each, which fits the chain budget measured in S1.

Caveats (repeated in ADR-021):

- Only the simplest cases were tested: an already initialised holding and a pre-inserted definition. Not tested: creating the definition through a real `new_fungible_definition` transaction with the engine PDA as authority in this harness (S1 did create a token with a PDA authority on a real standalone sequencer, for the faucet PDA), minting to a fresh holding (which needs the holder's authorisation in the same transaction per the token program's docs), or burning tokens held by an engine PDA (would need seeds on the burn call; the tested burn is signed by a user key).
- Deviation from the brief: it names `Token::Mint`; the tested and working path is `Token::MintWithAuthority` (external authority account). `Token::Mint` (self-authority, the definition itself must sign) failed as expected in the user-key test and cannot be driven by an engine PDA unless the PDA is the definition account.
- Prerequisites for later features, to be covered by Plan 2 tests: mint into a taker's possibly-fresh holding (F4 `take_debt`) and burn from an engine-PDA-held holding with seeds (`settle_debt`, F5). Neither was tested.
- `caller.mint_to` is open to any signer in this spike. The PDA only guarantees that `caller` is the sole minting path; deciding who may trigger a mint (for example only a settled debt auction) is engine logic and was not tested.
- Cycles are executor cycles from natively built guests, not proving cost; the `caller` side costs more than the token side because it decodes four accounts and builds the chained call.
- ADR: see ADR-021 in `docs/design-log.md`.
